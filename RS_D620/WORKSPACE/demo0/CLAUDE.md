# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Renesas RA (RA6M5 / R7FA6M5BH) embedded firmware project generated by RASC (the FSP Smart Configurator). Peripheral/BSP setup lives in `configuration.xml` and is code-generated into `ra/`, `ra_gen/`, and `ra_cfg/`; hand-written application code lives in `src/`.

## Build

CMake + Ninja, cross-compiling with the LLVM ARM Embedded toolchain (`cmake/llvm.cmake`).

```
cmake -DARM_TOOLCHAIN_PATH="C:/LLVMEmbeddedToolchainForArm-17.0.1-Windows-x86_64/bin" -DCMAKE_TOOLCHAIN_FILE=cmake/llvm.cmake -G Ninja -B build/Debug
cmake --build build/Debug
```

For a Release build add `-DCMAKE_BUILD_TYPE=Release -B build/Release`.

In VS Code: set `ARM_LLVM_TOOLCHAIN_PATH` in the environment (or `ARM_TOOLCHAIN_PATH` in `.vscode/cmake-kits.json`), select the "ARM LLVM - Ninja" kit, then build from the CMake status bar. Avoid spaces in toolchain/project paths — CMake and the build tools can misinterpret them as delimiters.

**Configure triggers a RASC codegen step.** On every CMake configure (unless `-DRENESAS_IDE=e2studio`), `cmake/GeneratedSrc.cmake` shells out to `RASC_EXE_PATH` (from `Config.cmake`, an e2 studio install path by default) to regenerate `ra_gen`/`ra_cfg`/linker content from `configuration.xml`. Without a real RASC install available, configure will fail unless `RENESAS_IDE=e2studio` is set (which no-ops `RASC_EXE_PATH` to `echo`) or `configuration.xml` hasn't changed since the last generation.

There is no test suite — this is bare-metal/RTOS firmware validated on hardware via flashing/debugging, not unit tests.

**Flashing/debugging**: via the Renesas Debug extension / SEGGER J-Link, target `R7FA6M5BH` (see `.vscode/launch.json`, `cmake.debugConfig` in `.vscode/settings.json`).

**Adding source files**: `cmake/GeneratedSrc.cmake` does `file(GLOB_RECURSE ...)` over `src/*.c` (and `ra/`, `ra_gen/`) — any `.c`/`.h` dropped under `src/` is picked up automatically on the next configure. No CMakeLists.txt edits needed. Note: `ra/`, `ra_gen/`, `ra_cfg/` are RASC-generated — don't hand-edit them; changes belong in `configuration.xml` (regenerated) or `src/`.

Build output directories (`build/Debug/`, etc., including the `.elf`/`.hex`/`.map` and Ninja/CMake internals) are checked into this repo's git history, so they will routinely show as modified after any build — that's expected, not a sign of stray changes.

## Application architecture

Entry point: `src/hal_entry.c` → `app_entry()` in `src/base_app/application.c`, which runs a simple state machine:

```
RESET -> STARTUP -> RUNNING (loop) -> RESTART -> STARTUP ...
                                    -> ERROR (halt)
```
`APP_STATE_RUNNING` repeatedly calls `app_func_run()`, `simulator_run()`, polls the control panel, and services console input/system event flags each iteration.

`app_func_reset/startup/restart/run` are `BSP_WEAK_REFERENCE` hooks with no-op defaults in `application.c`; a concrete app variant overrides them by providing its own strong-symbol definitions (see `src/sequencer/app_sequencer.c`).

**`src/application_common.h`** is the central switchboard: `APP_HAS_DEBUG_IO` / `APP_HAS_CONTROLPANEL` / `APP_HAS_CONSOLE` / `APP_HAS_CMD_SHELL` gate which optional subsystems get compiled in and included (console, control panel, debug GPIO). It also selects the RTOS backend (`APPCFG_RTOS_NONE` / `_AZURE` / `_FREERTOS` / `_ZEPHYR`) that `app_event_flag_*`/`app_delay_ms` are implemented against — currently bare-metal and Azure RTOS (ThreadX) are implemented; FreeRTOS/Zephyr paths are stubs (`#error needs implementing`).

Sample app variants under `src/` (each is a self-contained example of a config; see their `readme.md`):
- `base_app/` — minimal do-nothing skeleton (all `APP_HAS_*` off).
- `sequencer/` — power-rail sequencer sample (control panel on). `power_module.[ch]` models a multi-rail sequencer/fault-manager patterned after the TI UCD91320 PMBus power sequencer (rail state machine: OFF → SEQ_ON → ON → MARGIN_HIGH/LOW → SEQ_OFF, plus fault types OV/UV/timeout/GPI/watchdog).

Only one variant's `app_func_*` set should be linked in at a time — since sources are glob-included, keep unused sample variants' `.c` files out of `src/` (or excluded via `EXCLUDED_SOURCE_FILES` in CMakeLists.txt) to avoid duplicate-symbol link errors.

Supporting modules:
- `src/sequencer/CPAN/` — the "control panel" (`cpan_t` / `ControlPanel`): shared runtime status/register struct (status bits, general registers, LED state, port shadow/enable, simulated ADC channel values) used both by app logic and by console commands (`CP_commands.c`).
- `src/console/` — UART console with line/command parsing; wired to the app via `Console_callback` and `SYSFLG_CONSOLE_DATA`.
- `src/POP/` — debug GPIO helpers (POP/DROP/TOG a pin) for logic-analyzer instrumentation, gated by `APP_HAS_DEBUG_IO`.
- `src/simulator.[ch]` + `src/simulator_script.c` — drives `ControlPanel.adc_value[]` from a scripted table of ops (`SIMULATOR_OP_WAIT/RAISE/LOWER/FORCE/REPEAT/END`, each with a delay/divider/step) to simulate analog rail behavior without real hardware; `simulator_script.c` holds the actual script data (`srt_table_*`, `simulator_initial[]`) separately from the engine in `simulator.c`.

## Code conventions

- Headers use the pattern: brief banner comment, `#ifndef MODULE_H_`/`#define`/`#endif` guard matching the file path, `#include "application_common.h"` (or a narrower header) first, then a `/* USER INCLUDE */` marker line where app-specific includes go, then a `/* PUBLISHED functions */` block of the module's public API.
- `.c` files start with a short banner comment, then includes, then a `/* USER */` marker before file-local statics/globals.
- RTOS-conditional code is written as parallel `#if (APPCFG_RTOS == APPCFG_RTOS_NONE) ... #elif ... AZURE ... #elif ... FREERTOS #error needs implementing ... #elif ... ZEPHYR #error needs implementing #endif` blocks — follow this shape when touching RTOS-dependent code.
